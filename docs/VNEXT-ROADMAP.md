The previously referenced roadmap was not present in this checkout or the reviewed local branches. The released `@enzovezzaro/ai-auth-wallet` remains the compatibility baseline. vNext adds independently deployable services around the self-custodied wallet; it must not replace wallet identity with server-owned passwords or bearer-only agent identities. Public website authorization remains the relying site's responsibility. Deployment is gated on a passing authenticated shared-state flow.

## Delivery sequence

1. **Baseline and contracts:** capture current wallet/package behavior; specify plugin boundaries, protocol compatibility, tenant model and authorization invariants before implementation.
2. **Identity and authorization core:** create signed challenge/session contracts, durable nonce consumption, scoped grants and revocation policy. Keep private signing keys in the wallet.
3. **Tenant-safe persistence:** use a provider-neutral storage contract and validate Cloudflare SQLite-backed Durable Objects as the first adapter; implement tenant-scoped data access and isolation tests before adding public collaboration endpoints.
4. **Presence and collaboration:** add authenticated presence leases, room membership, event delivery, resync and coordination through Durable Object WebSockets, while keeping the transport behind the plugin contract.
5. **SDK and MCP adapters:** expose the same reviewed contracts to browser/Node SDK consumers and MCP clients; require capability checks for every tool or resource action.
6. **Dashboard and operations:** provide the smallest complete interface for wallet linking, consent, peers/rooms, activity and service health; add privacy-safe telemetry and operational procedures.
7. **Release gates:** run unit, contract, isolation, restart, security and browser E2E checks; publish versioned packages; deploy only after the production-like authenticated shared-state gate passes.

## Non-negotiable invariants

- The agent's private signing key remains under wallet control and is never uploaded as a service credential.
- A signature proves key control and signed content; it does not by itself authorize protected resources or prove human identity.
- Every protected operation binds identity, tenant, audience/resource, explicit capability, expiry and replay protection to server-side policy.
- Tenant identity is derived from verified membership/authorization, never trusted from an unverified request field.
- Credentials never appear in query strings, logs, analytics or public error messages.
- Shared state is durable and access-controlled; in-memory presence may be a cache, not the source of truth for authorization or persistence.
- Deployments and releases are claimed complete only from current registry, CI and production evidence.

## Current blockers and open decisions

- **Canonical roadmap source:** not found in the active checkout or reviewed branches. This tracker is derived from the explicit objective above.
- **Persistence/service target:** Cloudflare Durable Objects is the leading candidate because its free tier combines strongly consistent durable SQLite and WebSockets without a separately billed persistent machine. The free tier lists 100,000 Durable Object requests/day, 13,000 GB-seconds/day, 5 million reads/day, 100,000 writes/day and 5 GB SQLite storage; excess free-tier operations fail. It has no production uptime SLA or managed backup plan. Keep the provider swappable and fail closed at quota exhaustion.
- **Production shared-state credentials:** Wrangler is installed for the local Worker project, but `wrangler whoami` confirms there is no Cloudflare account authorization. No no-billing account verification has been established. Local tests now cover restart persistence; managed-runtime verification and free-account verification still precede deployment.
- **Vercel project access:** the connected Vercel MCP team API returns 403, but authenticated CLI access with the known team ID works. No MCP approval is needed for CLI inspection or project configuration.
- **Vercel project target:** `.vercel/project.json` links this checkout to `ai-auth` (`prj_IkvB070yd6cBpAPAXbgfuP4nk5w1`) and production serves `ai-auth-delta.vercel.app` at wallet `0.1.1`. The PR Vercel status points to `whelk` (`prj_ax46mz7fgEWWR5In9e7mkKdwVHsz`), not `ai-auth`; the projects have different build settings. The official `ai-auth` vNext preview is unverified. Do not treat the Whelk preview as production-project acceptance evidence. Vercel MCP project reads return 403, but authenticated CLI reads work. Production deployment remains gated on authenticated shared-state acceptance.
